P4 – Sharing. Accepted: share rows addressed by userId in the URL (PATCH/DELETE /shares/[userId]) instead of a DELETE with a body; every sharing route reuses authorizeDocument with canManageSharing, so non-owners who can see the doc get 403 and users with no access get 404; POST is an upsert, so sharing again just updates the role; self-share rejected with 400 and unknown email with 404 "No user with that email"; two-step inline confirm for delete instead of a native dialog; keepalive on the flush when leaving the page (plus a pagehide listener), skipped above ~60 KB because browsers cap keepalive bodies at 64 KB. Left as known limitations rather than built: an editor open in another tab is not notified when access is revoked or its role changes (next save fails with "Save failed – retry" or needs a reload), and there are no automated tests for the share routes (access rules are covered by the unit tests). Verified: build and 12 unit tests by the AI; I ran the full manual script myself with the seeded users in two browser sessions (Alice shares with Carol as viewer, Carol read-only, upgrade to editor, Carol edits, duplicate share only updates the role, revoke, Carol gets "Document not found", owner delete with confirm, flush on browser back) and everything passed.

P5 – File import (.txt/.md/.docx → new document). Kept the P0 split (the AI's suggestion, which I accepted): the server converts and sanitizes to HTML, the client turns HTML into Tiptap JSON with the same shared extension list as the editor, so unsupported markup is dropped instead of breaking it (POST /api/documents still validates the shape; a 2 MB file can exceed the ~1 MB content cap and is then rejected with a clear message). AI choices I kept: sanitize-html over DOMPurify (no jsdom), content checks beyond the extension (UTF-8/binary for text, zip signature + mammoth parse for .docx), and a dependency-free import-rules module so the browser doesn't bundle mammoth. AI's own bug caught by tests: the shell turned [\\/] into [\/] in a regex, and a test of its own had a wrong expectation for ".txt". Verified: build and 26 unit tests (including a real .docx fixture); the AI ran the production server and exercised the route with valid, invalid, empty, binary, fake .docx, oversized and unauthenticated requests. Not verified by the AI: the browser step (generateJSON → create → redirect), which has no automated test; I re-tested the full flow manually on the live deployment, including an XSS payload in .md, and everything passed. Known limits: images dropped, table structure dropped (cell text kept), no .doc/.pdf.
